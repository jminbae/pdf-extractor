# 문서 → Markdown 추출기: 사용자 피드백 반영 범위

갱신: 2026-10-23 · 상태: 구현 및 실행 검증 진행

이 문서는 요구 정리와 조사 근거입니다. 구현된 동작과 검증 결과는 [구현 계획](../implementation/2026-10-23-document-markdown.md), [검증 기록](../implementation/2026-10-23-verification.md)을 우선합니다. 앞서 작성한 [초기 조사안](./2026-10-23-document-markdown-plan.md)과 [서비스·UX 조사](./2026-10-23-benchmark-and-ux.md)는 후보와 근거 자료로 보존합니다. 최신 추가 요구는 드래그 입력, Windows 문서 폴더 중심 자동 저장, 설정의 기본 폴더 지정, 업데이트 버튼과 자동 업데이트입니다.

## 1. 기본 원칙

- **출력의 중심은 Markdown입니다.** 표·본문·각주 등 AI가 읽어야 하는 정보는 가능한 한 MD 안의 텍스트로 남깁니다.
- **LLM/VLM 없이 로컬 스크립트로 추출하는 것을 기본 경로로 정합니다.** 외부 유료 API, 생성형 표 수리, 자동 요약, 번역, 자동 의미 태깅은 초기 추출 기능에 넣지 않습니다.
- 스캔 OCR·표 영역/구조 인식에는 로컬 전용 인식 모델을 사용할 수 있습니다. 이것은 일반 LLM으로 문서를 다시 쓰는 단계와 구분합니다. API 사용료 없이 실행할 수 있지만 모델 다운로드·처리 시간·설치 크기는 발생합니다.
- **기존 논문 알고리즘과 구조를 살립니다.** 논문에서 잘 작동하는 GROBID/JATS/인용·참고문헌 경로를 일괄 교체하지 않습니다.
- 처리 범위는 논문·책·보고서·공문·스캔 등으로 확대합니다. 읽지 못한 부분은 표시하고 원문을 보존합니다. 모든 PDF의 완전한 추출을 검증 전에 보장하지 않습니다.
- 입력은 **파일 선택(여러 개 가능)**과 **폴더 선택** 두 가지를 기본으로 합니다. 감시 폴더·자동 개정판 관리·클라우드 동기화는 초기 범위에서 뺍니다.
- 사용자 흐름은 **선택 → MD 추출·저장 → 완료/오류 요약**으로 단순화합니다. 최신 후속 요청에 따라 **읽기 전용 MD 보기, 원본 검색, 원본과 MD의 스크롤·검색 결과·문단/표 클릭 위치 연동**을 포함합니다. 검수 화면을 거쳐야 저장할 수 있는 흐름을 만들지 않습니다. 앞서 위치 연결을 제외했던 결정은 이 요청으로 변경됐습니다.

## 2. HWP/HWPX: rHWP 직접 사용

**HOP은 설치하거나 자동 조작할 필요가 없습니다.** rHWP의 `export-markdown`이 직접 MD와 그림 자산을 생성합니다. 단순 문서는 이를 받아 문서 전체 MD로 묶거나 선택적으로 페이지/장 단위로 정리하면 됩니다. [rHWP 공식 CLI 계약](https://github.com/edwardkim/rhwp/blob/v0.8.7/mydocs/manual/cli_commands.md)

복잡한 표는 `export-tables --json`의 셀·병합·중첩 구조를 함께 읽고, 우리 스크립트에서 MD 표로 변환합니다. 병합 머리글은 `상위 머리글 / 하위 머리글`로 펼쳐 셀의 소속을 문자로 표현합니다. 평탄화한 표현과 원본 병합 구조는 내부에서 구분합니다.

본문에서 여러 행을 묶는 그룹명·기간·조건도 각 행의 소속을 잃지 않게 표시합니다. 병합으로 상속된 라벨은 그 사실을 기록하며, 원래 빈 셀이나 누락된 숫자를 임의로 채우지 않습니다.

직접 MD 출력에 실패하거나 읽기 순서·이미지·표에 결손이 있는 경우만 rHWP Document/query를 사용하는 보완 어댑터로 처리합니다. 처음부터 HOP 전체 UI·편집기를 이식하지 않습니다. rHWP exit code 0이나 MD 파일 존재만으로 표·그림 완전성을 판단하지 않고, 출력 수·경고·누락을 검사합니다. [exporter 소스](https://github.com/edwardkim/rhwp/blob/v0.8.7/src/cli/outputs/text.rs), [표 query](https://github.com/edwardkim/rhwp/blob/v0.8.7/src/document_core/queries/table_extract.rs)

## 3. PDF: 기존 논문 경로 + 일반 PDF 보완 경로

### 현재 코드에서 확인한 위험

| 확인한 분기 | 근거 | 보완 방향 |
|---|---|---|
| 한글 비율 15% 초과 시 본문만 비우고 참고문헌은 유지 | `single.py:360` | 범용 PDF 경로에서 이 논문 전용 제한을 적용하지 않음. 기존 논문 경로가 본문을 비웠다면 일반 경로 재시도 |
| 본문 문단 하나 이상이면 PMC/GROBID 결과 채택 | `single.py:481` | 본문·페이지 coverage를 검사한 뒤 완료 판단 |
| 책의 참고문헌에 있는 DOI를 문서 DOI로 오인할 가능성 | `inventory.py:99` | 단순 DOI 발견만으로 전체 책을 특정 논문 XML로 대체하지 않음 |
| 문서 전체 글자 합계로 텍스트층 유무 판단 | `inventory.py:84` | 본문은 스캔·참고문헌만 텍스트인 혼합 PDF를 페이지별로 검사 |
| 옛 배치 경로는 `is_primary && doi`인 파일만 처리 | `grobid_client.py:1080`, `pdf_fallback.py:1373` | 단건·폴더 배치 모두 DOI 없는 책과 일반 문서도 시도 |

소스 기준 디렉터리: `pubnexus/src/pubnexus/`. 이 사실들은 코드 검사 결과이며, 사용자가 겪은 특정 책을 재현한 결과는 아닙니다. 단건 앱에서는 DOI·초록이 없다는 이유만으로 본문을 차단하는 분기는 확인하지 않았습니다.

### 처리 흐름

1. 원 PDF의 페이지 수·텍스트층·목차·문자 좌표를 가볍게 조사합니다. 텍스트가 거의 없는 페이지는 스캔 후보로 구분합니다.
2. 논문 후보는 기존 논문 경로를 우선 사용합니다. 책·일반 문서로 판단할 근거가 있으면 일반 PDF 경로를 사용하며, 사용자가 `일반 PDF로 다시 추출`을 선택할 수도 있게 합니다.
3. 논문 경로의 결과도 원 PDF의 페이지별 원문과 비교합니다. 처음 일부만 처리했거나, 본문이 비었거나, 참고문헌 페이지만 남은 결과를 조용히 완료로 저장하지 않습니다.
4. 부족한 문서·페이지는 **일반 PDF 보완 경로**에서 다시 읽습니다. 원 문자·좌표 기반 본문과 표를 우선 추출하고, 필요한 곳에 비생성형 레이아웃/표 모델을 적용합니다.
5. 스캔·깨진 텍스트층만 로컬 OCR로 보완합니다. 일반 OCR/표 인식과 생성형 VLM 파이프라인을 구분하고 후자는 기본에서 끕니다.
6. 결과의 출처를 맞춰 합치고, 못 뽑은 페이지·표는 경고를 남깁니다. 참고문헌은 원문 일부로 유지하되 본문을 대체하지 않습니다.

본문 coverage는 원시 글자 수만 비교하지 않습니다. 페이지별로 본문·표·캡션·참고문헌 등에 대응한 텍스트와 미할당 영역을 비교합니다. 머리말·반복문구·합법적인 참고문헌 전용 문서를 고려하고, 임계값은 표본으로 정합니다. 분류가 불확실한 문단은 `other`로 남기며 삭제하지 않습니다.

특히 스캔 본문과 텍스트 참고문헌이 섞인 책은 문서 전체의 텍스트 존재 여부만으로 OCR을 건너뛰면 본문을 놓칩니다. 페이지별 native text 추출·OCR 필요 여부·실패 재시도를 따로 둡니다. 기존 `pdf_fallback`의 논문 전용 시작점·제외 규칙을 일반 문서 경로에 그대로 적용하지 않습니다.

기존 `_fulltext()` 후보 선택 지점뿐 아니라 한글·경계·캡션 등 후처리가 모두 끝난 **최종 저장 직전**에도 본문 급감/소실을 검사해야 합니다. 앞 단계에서만 검사하면 뒤 단계가 본문을 비우는 문제를 막을 수 없습니다. 일반 경로에서는 분류가 불확실한 참고문헌·짧은 문단·회전 텍스트를 일괄 삭제하지 않고 원문 블록으로 남깁니다.

### 기존 구조에서 추가할 최소 책임

- 최종 저장 전의 **완전성 검사**: 본문 없음·페이지 누락·표 빈 결과·캐시 엔진 버전 검사.
- 논문 경로가 부족할 때 호출하는 **일반 PDF 어댑터**.
- 중단 후 계속할 수 있는 **페이지/범위별 중간 저장**.
- 내부 정본에서 MD를 생성하는 **공통 내보내기**.

Docling을 쓰더라도 표준 PDF 레이아웃/표 경로를 비교하며, 전체 PDF 기본 엔진을 즉시 교체하지 않습니다. 기존 PyMuPDF·tablefill·GROBID의 유효한 결과를 재사용합니다. [Docling 구조](https://docling-project.github.io/docling/concepts/architecture/), [로컬 모델·표 옵션](https://docling-project.github.io/docling/usage/advanced_options/)

## 4. MD로 표현하기 어려운 내용과 탑재

**다른 형식 파일을 만들 수는 있지만, 대상 AI·위키가 그 파일이나 연결 자산을 읽는지는 별도입니다.** 파일을 첨부했다는 이유만으로 AI가 내용을 읽었다고 판단하지 않습니다. 기본 export는 MD 안에 읽을 수 있는 텍스트 표현을 남깁니다.

| 내용 | 기본 MD 표현 | 필요 시 보조 파일 |
|---|---|---|
| 단순 표 | 파이프 표 | 내부 셀 JSON |
| 병합·다단 머리글 표 | 머리글 경로·행 그룹 소속을 펼친 표, 또는 행별 항목 목록 | 원래 병합 구조 JSON, HTML 표, CSV |
| 수식 | 원문에서 변환 가능한 LaTeX와 원문에 있는 설명/원 script | 수식 이미지·원식, 변환 실패 경고 |
| 그림·차트 | 그림 링크·캡션, 추출 가능한 문자/원 데이터만 기록 | 원본 이미지·확보한 데이터 |
| 복원 불확실 표 | 읽힌 원문 텍스트와 미복원 표시 | 표 이미지·후보 구조 |

HTML 표를 허용하는 대상이면 MD 안에 HTML을 넣는 출력도 선택할 수 있습니다. HTML 표가 제거되는 대상에는 평탄화한 MD를 사용합니다. 일반 MD 표에 병합 표현 구문이 없다는 점과 대상 renderer의 지원은 구분합니다. [GFM 표 명세](https://github.github.com/gfm/#tables-extension-)

그림의 점·선으로 그려진 차트 수치를 근거 없이 생성하지 않습니다. 로컬 OCR로 읽은 글자와 캡션은 텍스트로 보완할 수 있지만, 이미지나 수식 표현을 모든 AI가 이해한다고 보장하지 않습니다.

기본 저장은 `문서.md + 필요한 assets/`입니다. 내부 정본 JSON은 재추출·수리를 위한 앱 자료이며, 사용자가 매번 여러 형식을 선택하거나 업로드해야 하는 흐름으로 만들지 않습니다. 대상이 MD 한 파일만 받으면 이미지·표의 문자 표현을 MD에 남기고 시각 정보의 한계를 표시합니다.

### 자동 저장 위치와 이미지 묶음

**자동 저장은 필수 요구입니다.** `추출`이 끝날 때 MD와 이미지가 함께 저장되며 별도 저장 버튼이나 파일마다 저장 대화상자를 거치지 않습니다. 화면에는 저장 위치와 `MD 열기 / 저장 폴더 열기`를 제공합니다.

기본 출력 위치는 최신 후속 대화에 따라 **Windows의 실제 문서 폴더 아래 `문서 추출기`**입니다. 파일·폴더·드래그 입력 모두 같은 정책을 사용합니다. 설정에서 기본 저장 폴더를 바꾸고 재실행 후에도 유지합니다. 저장 위치를 별도로 고르지 않아도 자동 저장합니다. 폴더 단위 입력에서 앱이 생성한 출력 폴더를 다시 원본으로 수집하지 않도록 구분합니다. 설정 변경은 이후 추출에 적용하며 기존 저장물은 이동하지 않습니다.

```text
원본 폴더/
  원본문서.pdf
  Markdown/
    원본문서.md
    긴제목을줄인저장이름--8e2d41a9.md
    assets/
      8e2d41a9/
        figure-001.png
        figure-002.png
```

MD에는 `![그림 설명](assets/8e2d41a9/figure-001.png)`처럼 상대경로로 연결합니다. 이미지 경로에는 긴 원본 이름을 반복하지 않고 짧은 문서 ID를 사용합니다. 내부 캐시나 AppData의 절대경로를 결과 MD에 넣지 않고 이미지를 출력 폴더에 함께 저장합니다. `Markdown` 폴더 전체를 옮기면 이 관계가 유지되며 MD 파일만 따로 옮기면 해당 이미지 폴더도 함께 옮겨야 합니다.

MD와 참조 이미지가 모두 저장되고 상대경로 검사가 끝나야 `완료`로 표시합니다. 이미지 미저장이나 디스크 오류는 부분 완료/실패로 구분하며 조용히 누락하지 않습니다. 동명인 서로 다른 원본의 출력은 자동 접미사 등으로 구별하고, 사용자가 편집한 기존 MD를 자동으로 덮어쓰지 않는 정책을 둡니다. 복잡한 개정판 관리 화면은 추가하지 않습니다.

현재 앱은 `store.py` 코드 기준 `%LOCALAPPDATA%\PDF Extractor\docs\...`에 내부 JSON, `figs\...`에 이미지를 저장하고 MD는 화면 생성에만 사용합니다. 이 PC의 기본 내부 루트는 `C:\Users\Bae\AppData\Local\PDF Extractor`이며 현재 프로세스에 `PUBNEXUS_STORE` override는 없습니다. 설치 앱의 별도 실행 환경까지 관찰한 것은 아닙니다. 위 MD 자동 저장 구조는 후속 구현 요구이며 이번 문서 수정으로 구현된 기능은 아닙니다.

### 긴 파일명·경로

원본 파일명은 변경하지 않으며 화면 상세와 내부 대응 정보에 그대로 보존합니다. 기본 목록에서는 이름의 일부를 줄여 보여 주고 눌러 전체 이름·저장 이름을 확인할 수 있게 합니다. 출력 이름은 필요할 때만 `축약 제목--짧은ID.md`로 조정하며, 이름 정규화·금지문자 치환·대소문자 무시 후 최종 이름의 충돌을 검사합니다. 짧은 ID가 충돌하면 길이를 늘리거나 별도 접미사로 구분합니다.

전체 절대경로와 각 구성요소의 길이를 별도 검사하고, 임시 저장 이름·이미지 경로도 검사합니다. Unicode는 UTF-16 길이를 고려하되 surrogate pair와 grapheme을 자르지 않습니다. Windows 예약 이름·끝 공백/마침표도 처리합니다. 파일명만 줄여도 부모 경로가 너무 길면 짧은 출력 위치를 제안합니다. 긴 경로 옵션만으로 모든 라이브러리·탐색기 호환성을 보장하지 않습니다. [Microsoft 경로 길이 규칙](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation), [Windows 파일 명명](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)

UI 시안은 대화 전용 위치에 저장했습니다. 원본 파일 내용 읽기·실제 변환·디스크 export는 수행하지 않는 시연이며 앱 소스에는 적용하지 않았습니다. 최초 두 레이아웃은 사용자가 AI스러운 UX라고 평가하여, 작은 도구막대·한 줄 파일 목록·하단 선택 파일 정보로 구성한 Windows 유틸리티형 단일 시안으로 교체했습니다. 큰 소개 문구·카드형 파일 행·큰 강조 버튼은 사용하지 않습니다.

새 시안의 전체 선택·추출·중지·재개·재추출, 긴 파일명 표시와 하단 저장 경로를 브라우저로 확인했습니다. 폭 약 990/702/318px에서 가로 넘침이 없고 넓은 터치 화면에서도 열이 유지됩니다. 재추출 성공 시 과거 경고는 정리합니다. 초기 시안에서 Unicode 정규화·예약명·동명 파일 표시도 확인했으며 이름 처리 로직은 새 시안에 유지했습니다. 이 검증은 실제 Windows 파일 경로 저장 시험을 대신하지 않습니다.

## 5. 사용자가 검토한 여섯 기능의 정리

| 항목 | 최신 범위 |
|---|---|
| 1. 문단·셀 클릭 → 원본 영역 | **최신 요청으로 포함.** 원본↔MD 양방향 문단/표 위치 이동·하이라이트, 검색 결과 이동과 스크롤 연동. 셀 단위 정밀도는 원본 위치 근거가 있을 때만 제공하며 근거가 부족하면 표·문단·쪽 수준으로 표시 |
| 2. 검수 대기열 | 별도 업무 시스템 없이 **변환 결과의 경고 목록**. 파일·쪽·사유·재시도 버튼만 제공 |
| 3. 선택 영역 재추출·전후 비교 | **유지.** 우선 쪽 단위 재추출. 표 영역만 재추출은 탐지/좌표 계약을 확보한 뒤 추가 |

경고 목록 예시는 `책.pdf / 73쪽 / 표 구조 미복원 / 다시 추출`, `보고서.pdf / 18쪽 / 텍스트층 깨짐 / OCR 재시도`입니다. 예시이며 실제 문서를 검사한 결과가 아닙니다.

빈 표·페이지 추출 실패·명백한 누락·두 추출 결과의 수치 불일치는 스크립트로 표시할 수 있습니다. **표의 모든 숫자가 옳은지를 자동 검증할 수 있다는 뜻은 아닙니다.** 합계·백분율 차이도 경고만 하고 자동 수정하지 않습니다. 사용자가 모든 경고를 해결해야 MD를 저장할 수 있게 막지 않으며 부분 완료를 표시합니다.

초기 화면 흐름은 `파일/폴더 선택 → MD 추출·저장 → 완료/오류 요약`으로 둡니다. 경고는 결과 요약으로 제공하며 사용자가 원본 검수 화면을 열어야 다음 단계로 진행하게 하지 않습니다. 엔진·모델·버전·내부 JSON은 내부 진단에 보존합니다.

## 6. 장문 안정성은 유지

화면은 진행 상태와 완료/오류 요약 중심으로 만들되 내부적으로는 페이지/작은 범위별 저장, 작업 취소·재개, 별도 worker timeout, 메모리·동시 작업 제한, export 재개를 포함합니다. 읽기 전용 MD 보기는 제공하되 긴 책 전체와 모든 이미지를 한꺼번에 DOM에 올리지 않는 표시 방식을 구현 시 검증합니다.

추출한 범위를 기록하고 전체 페이지 수와 대조합니다. 마지막에 목차·장 구조·연속 표·각주는 근거가 충분할 때 연결하며 불확실하면 분리·경고합니다. PDF 페이지와 인쇄 쪽수도 구분합니다. 페이지별 처리만 지원한다는 이유로 엔진 내부 메모리가 제한된다고 가정하지 않고 긴 문서로 측정합니다.

## 8. 기존 데스크톱 앱 UI/UX 개선 후보

사용자의 후속 질문에 따라 기존 첨부 화면과 `pubnexus/app.py`를 검토했습니다. 앱을 새로 실행하거나 설치한 평가가 아니며, 아래는 코드·화면에 근거한 제안입니다. 원본 파일 이동·복잡한 자료 관리 기능은 추가하지 않습니다. 원본과 MD의 위치 연결은 최신 요청에 따라 포함합니다.

가장 먼저 확인할 UX 과제는 **파일 하나를 골라 MD를 저장하고 찾기**, **폴더 전체를 처리하고 실패 항목만 다시 시도하기**, **긴 책의 진행과 중지를 이해하기**입니다. 이 제안으로 앱 코드를 변경하지 않았습니다.

### 후속 요청: 읽기 전용 MD와 원본 대조

사용자는 Windows 유틸리티형 시안을 선호한다고 밝히고 여러 상태 화면을 요청했습니다. 이어 각 MD를 직접 보고 원본과 대조하며 파일을 열 수 있기를 요청했습니다. 이에 `처음 시작 / 파일 선택 / 책 추출 중 / 중지와 재개 / 저장 완료 / 확인과 재시도 / MD 읽기 / 원본 대조` 8개 시안을 구성했습니다. 초기 시안의 `MD 원문` 표기는 사용자가 혼동한다고 지적했으므로 실제 제품에서는 기본을 `결과 보기`로 두고 마크다운 코드와 외부 프로그램 열기는 부가 메뉴로 정리합니다. 내부 보기는 읽기 전용이며 편집·저장 도구를 넣지 않습니다. 외부 프로그램의 편집 가능 여부를 앱의 읽기 전용 상태와 혼동하지 않습니다.

원본 대조는 우선 기존 PDF 표시 기능을 재사용하는 방향입니다. 다른 형식은 실제 렌더링 어댑터의 지원 여부에 따라 내부 표시 또는 외부 원본 열기를 적용합니다. 시안의 원본 영역은 표본 내용으로 만든 표시 예시이며 실제 PDF를 열어 대조한 결과가 아닙니다. 추출 앱 소스에는 적용하지 않았습니다.

8개 화면의 전환과 폭 약 1022/734/320px에서 가로 넘침 없음, MD 내용/원문 전환과 대조 2열, 읽기 화면에 편집 입력 없음, 처리 중 다음 문서 전환 시 읽기 포커스 유지, 목록 복귀 시 해당 문서로 포커스 복원, 한 문서 선택 시 진행 `1 / 1` 표시를 브라우저로 확인했습니다. 빈 목록에서 추가한 첫 파일의 저장 정보도 표시됩니다. 이 검증은 실제 문서 변환·PDF 렌더링·파일 열기·저장을 검증한 것은 아닙니다.

## 9. 최신 요청: 원본과 MD의 검색·위치 연동

사용자가 말한 함께 이동은 **화면의 스크롤과 문서 내 탐색**으로 해석합니다. 원본 파일이나 출력 폴더를 디스크에서 이동한다는 뜻으로 확장하지 않습니다. 앱 내부의 원본 보기와 MD 결과는 모두 읽기 전용으로 유지합니다.

| 동작 | 목표 동작 |
|---|---|
| 원본에서 단어 검색 | 결과 개수와 이전/다음 이동. 선택한 원본 검색 결과와 대응하는 MD 문단/표를 함께 표시 |
| MD에서 단어 검색 | 검색 결과에 대응하는 원본 쪽·슬라이드·시트/영역으로 이동 |
| 원본의 문단·표 클릭 | 해당 MD 문단·표로 이동하고 잠시 강조 |
| MD의 문단·표 클릭 | 원본의 대응 쪽과 영역을 표시하고 잠시 강조 |
| 한쪽 스크롤 | 현재 보이는 내용의 대응 위치를 기준으로 반대쪽 이동. 대조 화면의 `이동 연동` 스위치로 잠시 분리해서 볼 수 있음 |

스크롤 전체 높이의 같은 비율만 맞추면 다단 문서·이미지·긴 표에서 어긋나므로 내용의 대응 위치를 기준으로 이동합니다. 프로그램이 반대 영역을 이동시킨 이벤트가 원래 영역을 다시 이동시키지 않도록 사용자 입력 영역을 기준으로 연동합니다. 텍스트 선택·복사와 일반 링크 클릭을 이동 동작이 가로채지 않게 합니다.

검색 결과가 원본에는 있지만 MD에는 없으면 원본의 결과를 그대로 표시하고 `대응 결과 없음`으로 안내합니다. 존재하지 않는 MD 위치로 강제로 연결하지 않습니다. 검색·대조 하이라이트는 화면 위의 표시이며 원본에 주석을 저장하거나 MD를 수정하지 않습니다.

이 기능에는 추출 시 원본의 문서 버전·쪽/슬라이드/시트·문단/표 식별자와 좌표, MD 출력 범위 사이의 대응 정보를 보존해야 합니다. 반복 문구를 다시 검색하는 것만으로 연결하지 않으며, 한 원본 영역이 여러 MD 항목으로 바뀌거나 여러 셀이 하나의 표 항목으로 합쳐지는 다대다 관계를 허용합니다. 위치 정보는 별도 보조 데이터로 보관해 일반 MD 본문에 복잡한 코드를 노출하지 않습니다.

현재 앱의 PDF 표시는 PyMuPDF로 만든 페이지 PNG와 `<img>`이며 PDF.js는 사용하지 않습니다. 쪽 이동·확대·지연 로딩·현재 쪽 감지는 재사용 후보입니다. 본문 위치 정보는 일부 폴백 처리 중에는 존재하지만 최종 본문 JSON과 Markdown/HTML에 남지 않으므로 이 경로를 보완해야 합니다. 일부 표의 `pdf_span`은 재사용 가능성을 검증합니다. PDF.js로 전면 교체하는 것을 이 요구의 전제 조건으로 두지 않습니다. 코드 근거: `app.py:496`, `1802`; `schema.py:24`; `pdf_fallback.py:271`, `1182`; `tablefill.py:1852`; `render.py:358`. 실행 검증 결과는 아닙니다.

PDF, HWP 렌더, Office의 미리보기용 PDF는 서로 다른 표시 계층이므로 형식마다 대응 정보를 검증합니다. 구조 파서의 문단 ID가 변환 PDF의 정확한 좌표를 자동으로 제공한다고 가정하지 않습니다. 정확한 좌표가 없거나 대응이 중복되면 쪽·문단·표 수준으로 이동하고 `근처 위치` 등으로 정밀도를 표시합니다. 스캔 원본 검색은 OCR 텍스트와 단어 좌표가 있을 때 가능하며 인식 오류로 검색되지 않는 부분이 있을 수 있습니다.

긴 책은 전체 텍스트를 검색할 수 있는 색인을 사용하되 화면은 필요한 쪽과 MD 구간부터 표시합니다. 위치 데이터에는 원본·MD·표시 엔진/글꼴 설정의 버전을 연결하여, 원본이나 외부에서 수정한 MD와 맞지 않는 오래된 연결은 사용하지 않습니다. 외부 Word·한글·메모장 창의 스크롤을 앱과 함께 제어하는 것은 이 요구에 포함하지 않습니다. 앱 내부 표시 영역에서 연동합니다.

이 절은 구현 요구의 갱신이며 현재 8개 시안에 실제 검색·좌표 연동이 구현됐다는 뜻은 아닙니다. 근거와 보완할 계약은 [연동 대조 기술 조사](./2026-10-23-linked-comparison.md)에 정리합니다.

## 10. 구현에 들어갈 기본값과 남은 검증

큰 제품 방향과 기본 사용자 흐름은 정해졌습니다. 아래 기본값으로 계획을 진행할 수 있으며, 지금 단계에서 사용자가 추가로 결정해야만 계획을 완성할 필수 항목은 없습니다. 엔진별 품질·좌표 정밀도·메모리 한계는 결정이 아니라 구현 시 검증할 항목입니다.

| 항목 | 기본값 |
|---|---|
| 제품 목적 | 여러 문서의 내용을 AI·위키가 읽을 수 있는 Markdown으로 모으기 |
| 비용·처리 | 로컬 스크립트와 필요 시 로컬 OCR/인식 모델. 유료 API와 LLM/VLM 사용은 기본 경로에서 제외 |
| 입력 | 파일 하나·여러 파일·폴더 선택, 드래그 추가. 폴더 상시 감시·개정판 관리 UI는 제외 |
| 저장 | 기본 `문서\문서 추출기`에 MD·이미지를 자동 저장. 설정에서 변경하며 재실행 후 유지 |
| 원본·기존 결과 | 원본 내용·이름은 그대로 유지. 이름 충돌을 구분하고 외부 편집된 MD를 조용히 덮어쓰지 않음 |
| PDF | 기존 논문 경로 유지. 본문 소실/페이지 누락 검사와 일반 PDF·스캔 보완 경로 추가 |
| HWP/HWPX | rHWP 직접 연결. HOP 앱은 필수 의존에 넣지 않음 |
| 형식 확대 | PDF·HWP/HWPX·DOCX·PPTX·XLSX/CSV부터 순차 검증. 구형 Office·ODF·EPUB·HTML·메일 등은 기존 조사 우선순위에 따라 확대 |
| 화면 | 사용자가 선호한 Windows 유틸리티형. 작은 도구막대·파일 목록·상태·저장 정보 중심 |
| 읽기 | 앱 내부는 읽기 전용. 기본은 `결과 보기 / 원본과 비교 / 저장 폴더`. 코드 보기와 외부 파일 열기는 부가 메뉴 |
| 대조 | 원본·MD 검색, 양방향 문단/표 클릭 이동, 대응 위치 기반 스크롤 연동과 켜기/끄기 |
| 일부 실패 | 저장 가능한 내용은 저장하고 경고를 남김. 표 미복원과 파일 저장 실패를 구분하며 재시도 제공 |
| 긴 문서 | 작은 범위별 처리·중간 저장·중지/재개·지연 표시. 한 파일 실패가 전체 폴더 처리를 중단시키지 않게 함 |

구현 시 먼저 통과해야 할 기준은 다음과 같습니다.

1. 문제를 겪은 책에서 본문을 버리고 참고문헌만 저장하는 현상을 재현하고, 본문 보존 또는 명시적 부분 실패로 개선합니다. 기존 논문 표본도 함께 대조합니다.
2. MD와 연결된 이미지가 실제로 저장되며, 출력 묶음을 다른 위치에서 열어도 이미지 상대경로가 유지되는지 확인합니다. 긴 이름·동명 파일·쓰기 실패·재실행도 포함합니다.
3. 원본 검색 결과·문단·표의 위치를 MD와 양방향으로 연결합니다. 반복 문구·숫자·다단·페이지를 넘는 표에서 잘못된 일치가 선택되지 않아야 합니다. 대응이 없거나 불확실한 상태를 구분합니다.
4. 스캔 OCR 및 HWP/Office 미리보기의 정확도를 실제 표본으로 확인합니다. 지원 목록에 이름이 있다는 이유로 표시·검색·추출의 완전성을 보장하지 않습니다.
5. 긴 책과 폴더 배치에서 메모리·처리 시간·중지/재개·프로세스 실패 복구를 측정하고 한계를 기록합니다. 검증 전 수백/수천 쪽 처리 속도나 완전성을 약속하지 않습니다.

현재까지의 결과물은 연구·구현 계획·UI 시안입니다. 이 문서만으로 실제 추출 엔진과 설치 앱이 확장됐다고 판단하지 않습니다. 다음 단계는 위 순서대로 구현하고 검증하는 작업이며, 사용자가 요청했던 연구·계획 범위를 넘어 이번 대화에서 자동으로 구현에 착수하지 않습니다.
