# PPTX 첫 화면 지연 원인과 공개 렌더러 실측

2026-10-24 기준입니다. 사용자 PPTX 경로가 제공되지 않아 합성 자료만 사용했습니다. 실제 사용자 문서·기존 결과·설치 앱·AppData 캐시는 변경하지 않았습니다. 이 문서는 기성 렌더러의 조사와 독립 Chromium 벤치 증거이며 제품 통합·WebView2·실제 사용자 PPTX 성능 증거는 아닙니다.

## 원인과 선택

기존 `preview.py`는 LibreOffice가 PPTX 전체를 PDF로 저장한 뒤 첫 페이지를 제공합니다. 공개 PDF export의 `PageRange=1`도 프로그램 기동과 문서 로딩을 줄이지 못했습니다. 71장·71개 고유 JPEG·17,563,348B 합성 자료에서 전체 변환은 10.051초, 첫 장만 변환은 8.234초였습니다. 두 변환을 동시에 돌려도 첫 장 8.473초, 전체 10.594초여서 기본 중복 변환은 채택하지 않았습니다. 캐시 적중은 35–41ms였습니다. [공식 LibreOffice PDF 옵션](https://help.libreoffice.org/latest/en-US/text/shared/guide/pdf_params.html).

`/open?mode=result` 분리는 유효합니다. 별도 합성 HTTP 시험에서 원본 PDF 준비 9.874초 동안 저장 MD 응답은 105ms, 목록 최대 23ms, 다른 CSV 추출 완료는 1.619초였습니다. 이는 결과 열기를 변환 대기에서 분리한 증거이며 첫 원본 화면의 1–2초 목표를 해결한 증거는 아닙니다.

## Aiden 합성 브라우저 실측

공식 npm tarball의 SHA512를 확인한 뒤 공개 standalone 번들만 사용했습니다. CDN·서버 업로드·LLM·라이브러리 소스 패치는 없습니다. 새 Chromium155 context, 1400×1000 viewport, 로컬 HTTP, HTTP 캐시 `no-store` 조건입니다. 합성 PPTX는 71장·17,571,507B이며 실제 JPEG SHA가 서로 다른 71개임을 검사했습니다. 원본 슬라이드 크기는 960×720px입니다. 첫 화면 측정에는 JS import와 파일 fetch, ZIP 파싱, 모델 빌드, 지연 JPEG 노드 생성·decode, 글꼴 대기 및 2회의 requestAnimationFrame을 포함했습니다. 2RAF는 그리기 기회 지표이며 실제 사용자 창의 표시 지연 전체를 보장하지 않습니다.

| 요청 | 최종 측정 | 확인 범위 |
| --- | ---: | --- |
| 첫 슬라이드 | 219.0ms | 파일·모듈부터 실제 JPEG decode 및 본문까지 |
| 슬라이드 2 | 37.3ms | 요청한 장만 렌더, 병합표 7개 anchor 및 정확한 기호·숫자 |
| 임의 슬라이드 71 | 100.7ms | 요청한 장만 렌더, 차트와 JPEG |

각 요청 시 mount는 한 장이었습니다. 세 장의 실제 JPEG href 바이트 SHA는 해당 원본 JPEG와 각각 정확히 일치했습니다. 표는 `colspan=2`, `HER2+`, `HER2-`, `12.50%`, `>10`, 한국어 셀을 보존했습니다. 차트는 실제 canvas의 잉크 존재와 공개 모델의 categories `A/B`, values `13/29`를 별도로 확인했습니다. 스크린샷에서 두 막대와 범례·축을 확인했으나 이것을 전체 차트 시각 동등성으로 확대하지 않습니다. 페이지 오류와 외부 네트워크 요청은 0회였습니다. 선택하지 않은 나머지 슬라이드의 시각 품질, SmartArt·EMF·복잡 그룹·사용자 글꼴·애니메이션은 이번 벤치의 합격 범위가 아닙니다.

초기 151.9ms 관찰은 `onSlideRendered` 직후 이미지 노드가 아직 없는 측정 누락이 있었습니다. 엄격 이미지 gate를 추가한 v2는 false로 보존했고, JPEG 노드 생성과 decode를 필수로 한 최종 v3가 위 219.0ms입니다. 기존 실패나 초기 값을 덮지 않았습니다.

## 통합 시 지켜야 할 공개 API 경계

`parseZipLazyMedia(buffer, RECOMMENDED_ZIP_LIMITS)` → `buildPresentation(...,{lazySlides:true})`를 사용합니다. `externalMedia:'block'`, `pdfjs:false`를 명시합니다. 기본 external media 정책은 allow이므로 생략하지 않습니다. 네트워크·native bridge 격리와 ZIP 제한은 앱 호스트에서도 적용해야 합니다. [공식 API 및 보안 옵션](https://github.com/aiden0z/pptx-renderer/blob/v1.4.0/README.md).

공개 `renderSlideToContainer`의 `SlideHandle.ready`는 지연 media가 DOM에 삽입되는 단계까지 기다리지만 JPEG의 decode 완료를 보장하지 않습니다. `handle.ready` → 실제 이미지·CSS 배경 decode → fonts → 2RAF 순서가 필요합니다. 공개 `MediaResolver`에 350ms 지연을 준 대조에서 ready 359.3ms, decode 이후 390.4ms였고 resolve 1회·media 1개·materialized slide 1개였습니다. 임의 고정 sleep은 사용하지 않습니다.

검색용 `viewer.load(model)`과 외부 single handle만 사용할 때 기본 `fitMode:'contain'`은 ResizeObserver가 기본 list 렌더를 시작할 수 있었습니다. 이 부작용을 제외하려면 공개 옵션 `fitMode:'none'` 또는 명시적 width로 자동 resize를 끄고 호스트가 scale을 전달해야 합니다. 실제 오염 대조는 별도 보존했습니다. handle은 매 이동·확대 시 dispose하고 문서 종료 시 viewer도 destroy합니다. [공식 Viewer 구현](https://github.com/aiden0z/pptx-renderer/blob/v1.4.0/src/core/Viewer.ts).

`searchText`는 slideIndex/nodeId/nodePath/text/bounds를 반환합니다. nodeId는 OOXML cNvPr ID이고 bounds는 intrinsic slide px입니다. 현재 앱의 source.shape 트리 경로와 동일 ID라고 가정하지 않습니다. 기존 `shape_bbox_emu`·슬라이드 width/height를 정규화해 대응할 수 있지만 복잡 그룹 좌표는 별도 검증해야 합니다. `goToSlide`, `highlightSearchResult`, `setZoom`도 공개 API입니다. [공식 검색 API](https://github.com/aiden0z/pptx-renderer/blob/v1.4.0/src/search/TextSearch.ts), [노드 ID·좌표 파싱](https://github.com/aiden0z/pptx-renderer/blob/v1.4.0/src/model/nodes/BaseNode.ts).

## 배포 고지와 고정값

번들은 2,371,205B, SHA256 `eed96db79a8300ef66a57e8a5f4f2c06a5cb78ac30b7eecd5df921c05ac5069b`입니다. [vendor manifest](../../tools/presentation-renderer-manifest.json)에는 공식 tag lock과 대조한 18개 런타임 의존성의 버전·npm URL·SRI·고지 SHA를 기록했습니다. [수집 고지](../../tools/third_party_licenses/pptx_renderer/PPTX_RENDERER_NOTICES.md)와 24개 upstream 원문을 수정 없이 보존합니다. JSZip의 이중 라이선스는 MIT 조건을 선택하며, ECharts NOTICE·D3 고지, zrender BSD, tslib 0BSD, pako MIT/Zlib, inherits ISC, MPL·ECMA도 포함합니다.

MPL 구성요소 `mtx-decompressor` 1.4.2는 72,781B 공식 tag 소스 아카이브를 앱의 고지 옆에 함께 배포하도록 manifest에 필수로 지정했습니다. URL만 제공하고 끝내지 않으며 아카이브 SHA256은 `e4edf429b1614a8f7366a55cffe58b35c58e784f0d4719d209cc3aa28ef3d970`입니다. 원본 npm·소스 archive·JS는 DevCache에만 두고 저장소에는 작은 manifest와 고지 원문만 추가했습니다. [upstream 전이 고지](https://github.com/aiden0z/pptx-renderer/blob/v1.4.0/THIRD_PARTY_NOTICES.md), [Mozilla MPL FAQ Q8](https://www.mozilla.org/en-US/MPL/2.0/FAQ/), [MPL 3.2](https://www.mozilla.org/en-US/MPL/2.0/).

## 재현 근거와 남은 검증

생성물은 이 기기 `cache_root` 아래 `260725 PDF 추출/pptx-browser-1.2.5/`에 있습니다. `bench_server.py`, `browser-receipt.json`(preliminary), `browser-receipt-v2.json`(false), `browser-receipt-final.json`(최종), `handle-ready-and-image-hashes.json`(기본 contain 부작용 및 별도 이미지 SHA), `handle-ready-fit-none.json`(격리된 공개 ready 대조), `server-receipt.json`(입력 불변·TEMP 회수), `v3-slide-01/02/71.png`를 구분합니다. 기존 LO 근거는 `preview-1.2.5-benchmark/`, HTTP 분리 근거는 `preview-http-1.2.5/`입니다.

배포 전에는 실제 frozen WebView2에서 첫 원본 화면·임의 페이지 이동·검색·스크롤/확대 연결·문서 교체/취소·보안 sandbox·LibreOffice fallback 및 고지/대응 소스 동봉을 검증해야 합니다. 실제 사용자 PPTX 경로는 미제공 상태이므로 사용자 원본에서의 1–2초 성능이나 PowerPoint 시각 동등성은 아직 주장하지 않습니다.
