| 항목 | 결정 | 이유 |

| 본문 필드명 | **`body_text`** | S2ORC·CORD-19 관례. `sections` 는 구조를 가리킬 뿐 |
| 인용 표기 | **본문 제자리에 `[15]`** | 위첨자가 텍스트로 뽑히면 '효과가 있었다15,16' 처럼 본문 수치와 구분 불가 |
| 인용 범위 | `12-14` → `[12][13][14]` | 범위를 편다. `1-100` 처럼 넓으면 범위가 아니라고 보고 손대지 않음 |
| **참고문헌 내용** | **파싱하지 않는다. iCite(NIH) API 로 조회** | PDF 파싱 참고문헌은 구조적으로 못 믿는다 — DOI 순열 뒤섞임(한 편 125개 중 98개), 이웃 논문 혼입, 자기인용, 펀딩 문구 유입, 목록 0개가 전부 여기서 나왔다. **원장이 반복 지시한 사항이다. 다시 파싱으로 돌아가지 말 것.** |

### ⚠ GROBID on Windows — 소스 패치가 **필수**
공식 릴리스는 얇은 jar 뿐이고 윈도우에서 그냥은 안 돈다. `C:\grobid\grobid` 소스를 3곳 고쳐 빌드했다.
1. `build.gradle` — Mac/Unix 외 플랫폼에서 `throw RuntimeException("Unsupported platform!")` → 윈도우 분기 추가
2. `build.gradle` — `installDist` 에 `duplicatesStrategy = EXCLUDE`
3. `grobid-core/.../DocumentSource.java` — **이게 진짜 블로커**
   - 번들된 윈도우 pdfalto 는 **0.1 버전**(리눅스·맥은 0.5/0.6). kermitt2 는 윈도우 바이너리를 배포하지 않는다.
   - 0.1 은 `<TextBlock>` 없이 `<TextLine>` 을 내보내 파서가 NPE → HTTP 500
   - **`-blocks` 플래그**를 붙여야 블록이 생긴다(테스트 PDF 0개 → 146개)
   - `-noLineNumbers` 거부, 서버모드 `--timeout` 미지원 → 인자 축소 + 스레드 모드
- **JDK 21 필요**(GROBID 0.9.0 이 `JavaLanguageVersion.of(21)` 선언)
- **pdfalto 0.1 은 한글 경로 파일을 못 연다**(Cygwin 빌드). GROBID 서비스는 업로드를
  자기 tmp(ASCII)로 받아 처리하므로 무해하지만, **pdfalto 를 직접 호출하는 코드를 넣으면
  선생님 Dropbox 경로에서 즉시 터진다.**
- **표 검출이 리눅스보다 60% 나쁘다**(같은 134편: TEI 표 231 → 93). 그래서 파일럿 재처리에서
  **옛 TEI(데스크탑 Docker 산출)를 쓰는 쪽을 택했다.**
- 장시간 배치 중 서비스가 죽는다(175편 중 2회). **자동 재기동 필수.**

### ResearchMap 배포 함의
"첫 실행 때 공식 GROBID 다운로드"는 **불가능**하다. 우리가 패치해 빌드한 결과물
(`grobid-service/build/install/grobid-service/lib`, 183 jar, 240MB)을 직접 배포해야 한다.
Apache-2.0 이라 재배포는 가능하나 유지보수 부담이 생긴다.

## 6-A. 2026-07-26 오후 — 가장 큰 사고와 수리

### ⚠ 논문을 읽어들이는 **세 경로가 전부 죽어 있었다**

호출 즉시 `NameError` 로 죽는 상태였다.

**그 전날 고친 것이 산출물에 하나도 반영되지 않고 있었다.** 원장이 "나아진 게 없다"고

0자로 나왔다(앱이 뽑은 41편 전부).

**교훈**: 개명·리팩터 후에는 **모든 진입 경로를 실제로 한 번씩 돌려봐야 한다.**
나는 캐시된 TEI 로만 확인해서 폴백 경로를 한 번도 안 돌렸다.

### 앱 경로에만 수리 단계가 빠져 있었다
일괄 처리에는 있는 `recover`(문단 앞부분 복원)·`tablefill`(빈 표 재구성)이
`single.py` 에 없어 **앱 산출물만 조용히 질이 갈렸다**(표 161개 중 49개가 캡션만
남은 빈 표). 같은 일을 하는 경로가 둘이면 반드시 어긋난다.

### 그 밖에 고친 것
- **GROBID 검정창** — `.bat` 의 `start` 가 새 콘솔을 연다. `grobid_service.py` 신설:
  `javaw.exe` + `CREATE_NO_WINDOW` + `DETACHED_PROCESS`. 앱을 닫아도 서비스가 살아 있다.
- **배치 중 GROBID 사망** — 실제로 246편 재추출 도중 죽어 55편이 폴백으로 떨어졌다.
  `grobid_ready()` 가 매번 생존을 확인하고 되살린다(최대 3회).
- **합본 지면에서 앞 논문 DOI 를 잡던 것** — probe 는 '앞쪽에서 처음 보이는 DOI' 를
  쓰는데, letter 지면은 앞 편 꼬리와 이 편 머리가 한 쪽에 있어 앞 편 DOI 가 먼저
  나온다. `boundary` 로 이 본문이 놓인 구간을 찾아 그 구간의 DOI 를 쓰고,
  **Crossref 로 존재를 확인한 것만** 채택한 뒤 제목·저자를 다시 받는다.
- **저자명을 일부러 이니셜로 줄이던 것** — Crossref 가 given 을 전체로 주는데
  코드가 첫 글자만 따고 있었다.
- **절 제목** — `RESULTS › 소제목` 을 문단마다 반복하던 것을 실제 논문처럼 계층으로.
  제목이 아닌 것(인용번호 조각 `13-15`, 표 본문 `TABLE 2 …`, 초록 라벨 `Results:`)을
  화면에서 뺐다(2,493개 중 81개).
- **키워드** — 칩 자리에 논문 종류(`Journal Article`)가 들어가 있었다.
  `meta.keywords`(PubMed KeywordList) 신설 → MeSH 먼저, 저자 키워드 뒤에.

## 9. 2026-07-26 저녁 — 데스크탑(JMBOOK 아님)으로 옮긴 세션

노트북에서 **원장 데스크탑(사용자 `Bae`, D: 드라이브)** 으로 작업 환경을 옮겼다.
"컴퓨터를 바꿨더니 exe 가 안 뜬다"에서 시작해, 결국 **어느 PC 에서나 설치만 하면
GROBID 품질로 도는 상태**까지 갔다.

### 9.1 exe 가 죽던 진짜 이유 — cp949 에 em대시가 없다

두 번 죽었는데 원인이 같았다. **한글 윈도우 콘솔 인코딩(cp949)에 `—`(U+2014)가
없다.** (있는 것은 `―` U+2015.)

1. exe 를 프로젝트 밖(`Downloads`)에 혼자 두면 `config.yaml` 을 못 찾는다
   (frozen 상태의 ROOT 는 exe 가 놓인 폴더). 그 예외를 안내하는 로그 문구에 `—`
   가 있어 **except 블록 안에서 다시 예외** → 앱이 통째로 종료
2. GROBID 없는 PC 에서 `"분석 엔진 없이 진행 — PyMuPDF 폴백"` 을 찍다가 워커
   스레드가 죽어, **바로 다음 줄의 `_set("off")` 가 실행되지 않았다** → 화면이
   "준비 중"에서 영원히 멈추고 처리는 180초를 기다렸다

`utils.log` 가 인코딩 실패를 삼키게 고쳤다. `sys.stdout.reconfigure(...)` 만
믿으면 안 된다 — windowed exe 에서는 그 호출이 조용히 실패한다.

### 9.2 GROBID — 윈도우 네이티브로 **된다**

**8장의 "윈도우 네이티브 불가" 기록은 틀렸다.** 막던 것은 포맷이 아니라 인자였다.
자세한 것은 README 의 「GROBID 런타임」과 `tools/build_grobid_windows.ps1` 주석.
요지만: pdfalto 0.1 은 `-noLineNumbers`·`-onlyGraphsCoord` 를 모르고 `-blocks` 를
줘야 한다. 서버 모드의 `--timeout`·`--ulimit` 도 모르므로 스레드 모드로 보낸다.

  ※ 중간에 "파서가 `<BLOCK>`/`<TOKEN>` 을 기대한다"는 옛 메모를 믿고 `pdftoxml`
    2.0 으로 우회하는 헛수고를 했다. 0.9.0 파서는 **표준 ALTO** 를 읽는다.
    소스를 직접 확인하고서야 알았다. 남의 기록(내 것 포함)을 믿기 전에 소스를 봐라.

배포까지 만들었다. `tools/package_grobid_runtime.ps1` 이 1,561MB → zip 436MB 로
줄이고(JDK 는 jlink 49MB, 다른 OS 용 pdfalto·특허 모델·hdf5 제거), 앱이 없으면
Releases 에서 내려받아 `%LOCALAPPDATA%` 에 깐다. 최초 1회 82초.

### 9.3 그림 — 다시 그리지 말고 원본을 꺼낸다

7장 "그림 이미지가 하나도 없다"는 이미 노트북에서 해결돼 있었다. 화면에 안 뜬
이유는 **저장 위치와 읽는 위치가 달라서**였다(figclip 은 정본 JSON 옆, 화면은
`store.figs_dir(sha1)`). `single.py` 9줄로 끝났다.

이어서 화질을 고쳤다. 원본이 1418×1145 인 사진도 170dpi 로 다시 그리면 816×600 이
된다(화소의 30%). 내장 이미지 한 장짜리 그림은 원본을 그대로 꺼낸다.
**25편·43장에서 16장이 원본으로 바뀌고 총 화소 1.73배.**

원본을 쓰면 **틀리는** 경우는 렌더로 되돌린다. 특히 사진 위 벡터 도형 —
사각형 하나로 두르거나 깔아 놓은 것만 장식으로 보고, 그 밖은 내용일 수 있으므로
렌더로 간다. **화살표를 잃으면 화질보다 큰 손실이다**(실측: 테두리는 0.2pt·항목1,
화살표는 28×54·항목6).

### 9.4 보는 방식 — 아래로 뛰지 않는다

인용 `[15]` 와 본문 `Figure 1` 을 누르면 **그 자리에 카드**로 뜬다. 논문을 읽다
인용을 확인하는 것은 "곁눈질"이지 "이동"이 아니다. 목록으로 가려면 카드 안에서
한 번 더 누른다.

그 과정에서 **이미지에 width/height 가 없으면 링크 착지점이 밀린다**는 것을 배웠다.
크기 없는 `<img>` 는 로드 전 높이가 0 이라, 자리를 계산해 놓은 뒤 그림이 도착하며
문서를 밀어낸다. PNG·JPEG 헤더만 읽어 크기를 넣었다(의존성 0).

### 9.5 배포 — 백신이 exe 를 지웠다

Defender 가 `Trojan:Win32/Wacatac.H!ml` 로 잡고 파일을 삭제했다. `!ml` 은 서명
일치가 아니라 머신러닝 추정이고, PyInstaller `--onefile` 이 실행 시 자기 안을
임시폴더에 푸는 동작이 악성코드와 구조가 같아 늘 걸린다.
**`--onedir` + Inno Setup 설치프로그램**으로 바꿔 없앴다(스캔 통과 확인).

### 9.6 첫 실행에서 조용히 저품질로 내려가던 것

"새 PC 에서 설치만 하면 되느냐"는 물음에 답하려고 실제로 재현해 보니, 처리 시작
시 **180초만 기다리고** 폴백으로 떨어졌다. 첫 실행은 엔진 435MB 를 받는 중인데
회선이 느리면 그 안에 못 끝난다 → **말없이 저품질 산출물**. 결판이 날 때까지
기다리도록 고쳤다. 진행률도 "준비 중 67초"가 아니라 "설치 중 67%"로 나눴다.

  **교훈**: "되는지" 를 물어보면 반드시 그 조건을 **실제로 만들어** 돌려봐라.
  물어보지 않았으면 첫 사용자가 저품질 결과를 받았을 것이다.
